# ReadBridge 图书导入、渲染与 AI 重构工作文档

更新日期：2026-09-08  
状态：阶段 0—6 已实现；真实 provider 与 Tauri 打包需在具备外部条件的环境中验证  
依据：仓库审查、自动化回归测试、类型检查、lint、生产构建与依赖审计。

## 1. 目标与执行原则

使用成熟 SDK 和解析工具替换手写的通用机制，保留 ReadBridge 的逐句阅读、语言学习辅助和自定义规则能力。

**渐进式指每次变更可以独立 review、运行和验证，不要求保留旧的内部实现。** 单个阶段可以彻底删除和替换一个模块；不把整个项目重写混在同一份 diff 中。阶段内部为维持运行可以短暂保留适配层，后续调用方切换完成后必须删除。

- 保留功能意图和用户数据，不保留导入丢文、解析不稳定、缓存过期规则错误等旧缺陷。
- 每阶段只解决一个主要问题，完成验收并提交审查材料后，再推进依赖它的阶段。
- 本文同时记录已经完成的实现和仍需外部环境验证的事项；没有清空书籍、历史、设置或书签数据。
- 使用版本控制保留旧实现。不要长期维护新旧两套 AI 管线，也不为未出现的需求建立复杂兼容系统。
- 不把框架大版本升级、全站 UI 重设计和业务重构混在一起。依赖确实要求升级时，单独说明和审查。

## 2. 已确认的产品边界

| 事项 | 决定 |
| --- | --- |
| 图书形态 | 继续纯文本、逐句学习；不做 EPUB 原排版阅读器 |
| 导入格式 | 保留 EPUB、TXT、Markdown；不新增 AI 整理图书流程 |
| 句子规则 | 保留多条自定义规则；每条分别选择 TEXT、SIMPLE_LIST、KEY_VALUE_LIST、MD |
| 内容块系统 | 本轮不做一条规则自由组合多类内容块的系统 |
| 结构化输出 | 需要结构的句子分析使用 JSON Schema；纯文本和 Markdown 直接返回文本流 |
| 思考展示 | 必须可以查看；与正文分开处理和展示 |
| AI 接入 | 主流官方 provider 使用对应适配器；保留自定义地址、模型和兼容接口入口 |
| 兼容范围 | 不保证任意中转站全部能力；不为不支持结构化输出的分析接口预建多级降级系统 |
| 重构方式 | 按可审查阶段逐步替换；允许彻底重写内部实现 |

以下作为本计划的实现建议，进入相关阶段时确认具体行为：聊天和词语解释继续流式 Markdown；句子分析中的 TEXT 和 MD 直接返回文本流，列表类结果使用 JSON schema。

### 尚未决定，但不阻塞本工作文档

- **Tauri 的最终去留**：本轮保留现有套壳与配置，不新增桌面专属代码。本机没有 Rust/Cargo，无法完成安装包验证。
- **Web 部署与密钥路径**：继续由用户自填密钥并从浏览器直连 provider。已删除与静态导出矛盾的 LLM 运行时代理；跨域错误直接作为请求错误展示。
- **真实模型验证**：自动测试不读取本地密钥。官方 OpenAI、Anthropic、Google 和 OpenAI Compatible 工厂均已验证可构造，真实账号能力和跨域行为仍需使用者配置后验证。

## 3. 现有链路与重构依据

### 3.1 图书与阅读

```text
BookUploader → ServerUpload → BookService → Epub / TXT / MD
→ Book.chapterList[].paragraphs → Dexie
→ DB.paragraphs2Lines → readingProgress.sentenceChapters
→ ReadArea → 选句 / 书签 / AI 分析 / TTS
```

这里的 ServerUpload 实际处理浏览器 File，并不是上传到服务端的接口。阅读区使用纯文本句子，AI 回答另走 Markdown 渲染器。

| 代码位置 | 发现及影响 |
| --- | --- |
| `services/Epub.ts` | 靠目录前缀猜章节路径；无标题章节被跳过；只抽取 p；解析失败可能存成包含 ZIP 文件列表的“章节” |
| `services/MD.ts` | 首个 h2 前内容可能丢失；先抽 p 再抽 li、blockquote，可能重排和重复；部分块内容未纳入 |
| `services/TXT.ts` | 固定 UTF-8；需要确认非 UTF-8 文件的预期处理 |
| `services/ServerUpload.ts` | 上传界面按扩展名接受，处理层按 MIME 拒绝，识别规则不一致 |
| `services/DB.ts` | 存储层同时负责分句；中文正则遗漏无句末标点尾句；分句缓存没有算法版本 |
| `types/book.ts` | 进度和书签按章节、句子下标定位；重新分句会影响旧位置 |
| `app/read/components/readArea/index.tsx` | 整章生成 DOM；滚动定位和进度保存互相影响，优化需以测量为依据 |

### 3.2 AI 与结果展示

```text
OpenAI SDK 或手写代理 SSE
→ reasoning 字段转成 <think> 字符串
→ 手写 p / li 输出解析
→ 组件再次拆分思考和正文
→ 保存缓存
→ 命中缓存后重新拼标签、回放生成器、再次解析
```

| 代码位置 | 发现及影响 |
| --- | --- |
| `services/llm/clients/openai.ts` | 创建客户端立即 check 并发送 hi；任意直连错误均触发代理；存在手写 SSE 和思考标签转换 |
| `services/llm/index.ts` | provider 全部走 OpenAI 兼容接口；工厂直接读取 Zustand |
| `utils/generator.ts` | 自己处理分块标签边界和 HTML 列表；协议和业务输出耦合 |
| `SiderContent/index.tsx`、`cpns/Sentences.tsx` | 调度、流消费、思考状态、缓存和渲染混合；缓存写入嵌在 React 状态更新回调中 |
| `SiderChat/index.tsx` | 另一套思考计时与流消费；停止提示进入正文，可能进入后续聊天上下文 |
| `SiderContent/index.tsx` 词语解释 | 直接累加生成字符串，没有与句子和聊天统一的思考展示机制 |
| `utils/cache.ts` | 缓存身份缺少模型、提示词内容、输出格式等变化因素 |
| `store/useLLMStore.ts` | 默认模型保存对象副本；provider 配置更新与运行中客户端需要明确同步规则 |
| `next.config.js`、`app/api/llm/proxy/route.ts` | 静态导出与运行时 POST 代理不一致；静态产物本身不能执行该代理 |

## 4. 目标架构

### 4.1 AI：一个通用执行流程

```text
阅读功能 / 聊天
→ 构建任务输入、规则、上下文、输出契约
→ AI 执行层（状态、取消、结果校验）
→ AI SDK provider + 请求通道
→ 结构化结果 / Markdown + 独立 reasoning
→ 通用展示状态 + 完成结果缓存
```

- 优先采用 Vercel AI SDK Core，使用 Zod 定义需要结构化的结果 schema。安装版本需通过 React 18、Next 14、运行环境及实际 API 的最小验证。
- 官方协议由对应 provider 适配；兼容服务使用 OpenAI Compatible provider。不要把所有官方服务强行转成同一上游协议。
- 请求配置显式传入服务。服务内部不读取 UI store，不弹 Ant Design 消息，不在构造阶段发送测试请求。
- 设置层管理 provider、模型引用、参数；工厂按当前配置解析。默认模型避免长期持有失效副本。
- 模型能力、参数差异集中在适配边界。不要给不支持的模型无条件传 temperature、top_p 等参数。
- 不引入 Agent 编排、工具调用、RAG 或工作流框架；当前业务不需要这些能力。

### 4.2 句子输出契约

每条规则仍只选择一种展示类型。程序按类型选择纯文本流或结构化 schema，模型只生成内容。

| 类型 | 模型结果示意 | 渲染方式 |
| --- | --- | --- |
| TEXT | `...` | 普通文本流 |
| SIMPLE_LIST | `{ "items": ["...", "..."] }` | 列表 |
| KEY_VALUE_LIST | `{ "items": [{ "label": "...", "description": "..." }] }` | 标签与说明 |
| MD | `## ...` | Markdown 文本流 |

- 任务 ID、规则 ID、展示类型和运行状态由应用提供，不让模型重复生成。
- 规则提示词负责分析内容；输出契约和应用级格式说明负责呈现。内置提示词删除旧 HTML 要求。
- 自定义提示词原样保留；其中可能存在旧 HTML 要求，迁移时提示检查，不静默重写用户文本。
- 使用简单对象、字符串、数组和必要字段，避免复杂 schema 降低跨服务兼容性。
- 校验结构不等于保证分析正确，仍需用代表性句子检查内容质量和自定义规则的效果。

### 4.3 流式状态、思考和取消

- 通用状态至少区分待执行、生成中、完成、取消、失败。思考是否正在输出单独表示。
- reasoning 与结果独立接收；思考区域可展开查看。只展示服务实际返回的思考或摘要，不要求模型额外生成思考字段。
- 供应商已提供独立 reasoning 时直接使用。仅对正文内带 think 标签的适配需求启用 SDK 通用中间件；组件不解析标签。
- TEXT 和 MD 直接随文本流更新。结构化流的部分结果用于预览，完成后才进行最终校验；不要把不完整对象当成可缓存结果。
- 列表展示策略由 SDK 能力验证决定，须确认逐项出现的体验。
- 每次执行有独立 requestId 和 AbortController。切句、切书、卸载或新请求后，旧执行不得继续更新当前 UI 或写成功缓存。
- SDK 已有的重试行为先明确，再制定应用策略，避免重复重试叠加。鉴权、限流、网络故障和不支持的能力分别呈现。
- 取消与错误为状态，不拼进模型正文；聊天上下文转换只包含应发送给模型的数据。

### 4.4 缓存与历史

- 缓存存最终业务结果和可选 reasoning，不存生成器、信号或未完成对象。
- 命中后直接恢复完成状态，删除伪造网络流的路径。
- 缓存身份包含完整输入、书籍身份（适用时）、provider/模型身份、有效生成参数、提示词内容、输出契约版本；不使用密钥本身生成缓存键。
- 换模型、修改规则、修改输出类型等行为需要实际验证失效。将来增加上下文时，上下文也进入缓存身份。
- 新结果使用独立版本或命名空间，旧缓存不作为新结果读取。旧缓存清理单独说明，不连带删除书籍、历史和设置。
- 现有缓存开关、容量、有效期等用户可见设置保留；内部时间槽结构可在确认需要后替换，不提前扩大工作量。
- 聊天历史兼容旧正文和 reasoningContent。需要改 schema 时提供有版本的迁移；不要把新 SDK 的临时对象直接持久化。

### 4.5 图书处理

```text
File → 格式识别 → 格式解析器 → 规范化章节/段落
→ 书籍存储 → 独立分句服务 → 阅读展示
```

- EPUB 解析器候选包含 EPUB.js，先验证浏览器使用、章节顺序、路径、目录、资源释放和包体；仅使用所需解析能力，不接管阅读区排版。
- Markdown 使用按文档顺序遍历的语法树或等价的结构化解析方式，避免 HTML 转换后分批抓取造成乱序。图片不要求渲染，但可读文字块的保留规则需明确。
- TXT 保留原文本顺序与空段规则；编码支持范围在样本验证后明确。识别失败应提示，不默默导入乱码。
- 分句从 DB 抽出，明确语言、段落边界、算法版本。可评估 Intl.Segmenter 等方案，但需用目标语言样本验证。
- Compromise 还用于词语切分、词性着色；替换分句不意味着能直接删除该依赖或这些功能。
- 旧书默认保留既有分句和位置，新书使用新版解析与分句。不要在打开旧书时静默重建。
- 当前存储没有保留原始导入文件；已经丢掉的内容无法从旧纯文本恢复。重新导入属于显式流程，并需要考虑 fileHash 去重。
- 章节编辑、排序、删除后必须处理派生句子和位置失效；旧进度迁移需单独验证，必要时保留原文定位辅助。

### 4.6 性能与渲染

- 不以现代电脑性能为理由忽略主线程阻塞，也不预先做所有优化。
- 先测导入耗时、UI 是否响应、长章打开与滚动、并行分析时的更新开销、书架读取量。
- 同步解压解析导致明显卡顿时，将解析任务移到 Worker；应有开始、完成、失败和取消的明确反馈。
- 流式更新过频时合并 UI 更新；成功完成前仍保证最后一段内容落入状态。
- 长章虚拟列表只在测得瓶颈后引入，并同时验证文本选择、滚动恢复、选句和书签跳转。
- Markdown 先保留 react-markdown；Streamdown 为候选，需验证依赖、样式、公式和流式体验。渲染器迁移应是独立 diff。
- AI Markdown 的原始 HTML 支持需按现有需求审查，明确允许的元素、链接和资源规则；不沿用“只排除 iframe 就够了”的隐含边界。

## 5. 阶段划分与 review 边界

### 阶段 0（完成）：功能基线与最小选型验证

**变更范围**：记录运行、构建、类型检查现状；准备小型测试设施和导入样本；验证 SDK，不切换生产调用。

**产出**：现有功能清单、已知失败、选定依赖版本、少量真实 provider 的验证结果。

**验收**：确认两种文本流、两种结构化输出、reasoning、流式部分结果和取消可用；明确结构化 API 与 SDK 版本的组合。需真实 API 验证时，只使用用户提供且允许测试的配置，不读取或输出秘密；缺少条件如实标注未验证。

### 阶段 1（完成）：provider 与请求通道

**变更范围**：新 AI 适配层、设置解析、请求通道及最小必要的构建配置。输出和 UI 行为暂时保持。

**前置决定**：确认 Web 使用直连还是运行时代理、代理由谁部署、密钥经过哪里，以及 Tauri 如何继续访问。此决定完成前，不删除静态导出或桌面支持。

**过渡方式**：必要时通过薄适配器满足旧 Client 接口；明确标记阶段 3 删除。不要为适配层再实现一套 SSE。

**验收**：无初始化 hi 请求；配置修改生效；直连/代理行为明确；成功、鉴权失败、限流、取消可区分；被支持的运行方式通过构建和请求验证。

### 阶段 2（完成）：句子输出契约与新缓存

**变更范围**：TEXT/MD 文本流、列表类 schema、句子任务执行、结果状态、句子展示、新缓存读取写入及内置提示词。

**验收**：四类卡片与自定义规则仍可用；流式结果和思考可见；快速切句无旧结果覆盖；中断和失败不写成功缓存；配置变化正确失效；命中直接展示。

**删除项**：不再使用的 HTML 输出解析与缓存流回放；若仍有调用方则列明下一阶段删除位置。不得留下默认走旧解析的隐性回退。

### 阶段 3（完成）：词语解释、聊天统一执行与展示状态

**变更范围**：词语解释、聊天、上下文转换、思考组件、历史兼容；保持其 Markdown 内容体验。

**验收**：查词、上下文/整章聊天、提示词选择、停止、历史恢复和思考展开可用；切换历史或新建会话后旧流不污染新会话；状态提示不进入正文。

**删除项**：旧 Client 协议适配器、手写 SSE、重复 think 解析和计时逻辑，以及旧结果生成器管线。搜索所有调用方确认已完成切换。

### 阶段 4（完成）：图书解析替换

**变更范围**：格式识别、EPUB/TXT/MD 解析及导入错误反馈；尽量保持现有 Book 存储契约。

**验收**：EPUB 相对路径、无标题正文、不同目录结构；Markdown 前言、列表、引用顺序与去重；TXT 换行与编码边界；不以占位错误章节冒充成功；重复导入和批量导入仍可用。

### 阶段 5（完成）：分句与位置管理

**变更范围**：分句服务、版本信息、派生数据失效、章节编辑联动和必要的数据迁移。

**验收**：中文无标点尾句、英文缩写/引号、混合语言、空段不丢正文；旧书不静默重分句；进度、书签、选句、批量句子分析、词性着色和 TTS 触发仍正常。

### 阶段 6（完成）：按测量优化性能与可选渲染器替换

**变更范围**：一次只提交一种优化，例如 Worker、流式更新合并、书架摘要读取或虚拟列表。Markdown 库替换另成一份审查变更。

**验收**：同设备、同样本、同操作比较前后指标；确认功能没有因优化退化。不为完成阶段而强行增加库。

## 6. 验证与数据保护

### 必须覆盖的回归场景

- AI：两种文本流、两种列表结构、空结果、截断、schema 不匹配、reasoning 有/无、主动取消、快速连续切句、多个规则同时执行、provider 配置更新。
- 缓存：命中、过期、改提示词、换模型、改输出类型、取消后不命中、旧缓存隔离。
- 聊天：上下文、整章、多轮、停止、新建会话、切历史、旧历史恢复。
- 图书：EPUB 嵌套路径和无标题正文；Markdown 含前言及交错块；TXT 空行与换行；中文尾句和英文边界；旧书位置与章节编辑。
- 运行方式：最终明确支持的 Web 构建/部署方式；若保留 Tauri，验证其构建和实际请求路径。

测试集中在以上容易回归的边界，不为每个薄包装函数编写镜像测试。SDK 流可用可控模拟验证竞态和取消；真实 provider 测试用来验证接口兼容性，两者不能相互替代。

在涉及持久化迁移前准备可恢复备份或导出路径。书籍、阅读进度、书签、提示词、provider 设置、聊天历史均需明确保留。迁移失败应留下旧数据，并有可说明的恢复方法。

## 7. 每阶段的审查交付模板

1. **问题与行为变化**：用户在什么操作下会看到怎样的前后差异。
2. **边界**：涉及哪些模块；哪些旧路径被彻底移除；哪些临时适配仍在，何时删除。
3. **数据影响**：是否改持久化格式、如何迁移、如何恢复、哪些旧缓存不再使用。
4. **验证证据**：执行过的检查、样本、实际 provider、结果；没有验证的条件单列。
5. **待决定事项**：只列阻塞下一步的真实产品决定，不能通过沉默推断同意。

实现按上述阶段组织，便于按模块 review。编译或构建通过不能替代真实账号与桌面安装包的用户流程验收。

### 2026-09-08：阶段 1—3 完成

- 新增统一 AI 执行层：provider 工厂只负责协议差异，生成服务统一处理正文、reasoning、结构化输出和取消。
- 设置页支持 OpenAI、Anthropic、Google Gemini、OpenAI Compatible 四种协议；旧 provider 记录按 ID 兼容推断，不要求清空设置。
- TEXT 与 MD 保持直接文本流；SIMPLE_LIST 和 KEY_VALUE_LIST 使用 Zod/JSON Schema，并在完成后校验。
- 句子、查词和聊天均使用同一执行层；快速切句、切词、新建聊天或切历史会使旧请求失去写入当前界面的资格。
- reasoning 独立显示，不再把 `<think>` 拼入正文。旧手写 SSE、HTML 标签解析、缓存生成器回放、初始化 `hi` 请求及 LLM proxy 已删除。
- v2 缓存保存最终业务对象和 reasoning；缓存键覆盖书籍、输入、规则内容、输出类型、provider、模型及生成参数。旧缓存保留在存储中但不会命中新命名空间。
- AI provider 改为按协议动态加载。生产构建中侧栏首屏由约 795 kB 降至 690 kB，减少约 105 kB。

### 2026-09-08：阶段 4—5 完成

- EPUB 严格从 `container.xml` 定位 OPF，再按 OPF 所在目录解析 manifest 相对路径；无标题章节使用稳定回退标题，解析失败直接报错。
- Markdown 按 token 原顺序生成段落，保留首个二级标题前的前言，并避免列表、引用的二次抓取和重排。
- TXT 支持 UTF-8 BOM、UTF-16 LE/BE BOM；非法 UTF-8 回退 GB18030。上传格式统一按扩展名识别，避免浏览器 MIME 为空时误拒绝。
- 分句从 Dexie 中抽到独立服务；英文使用 sbd，其他语言使用 `Intl.Segmenter`，并保留无句末标点的尾句和段落边界。
- 新导入图书和编辑过章节的图书使用分句格式 v2。旧书已经存在的分句与下标保持不变；旧书尚未生成过的章节使用新算法。
- 章节内容被编辑时清除派生分句并把位置重置到首章；纯元数据修改不再无条件清除阅读进度。
